# Как устроен механизм

Сам паттерн Token Bucket живёт в одном файле: `src/ratelimit/core/bucket.py`, класс `TokenBucket`. В нём около 76 строк, и ни HTTP, ни Redis там нет. Всё остальное в проекте нужно, чтобы этот класс работал в реальных условиях.

## Состояние ведра

| Поле | Что это |
|---|---|
| `capacity` | Размер ведра: сколько токенов в нём максимум |
| `refill_rate` | Сколько токенов возвращается за секунду |
| `tokens` | Сколько токенов в ведре сейчас |
| `last_refill` | Когда `tokens` пересчитывали в последний раз |
| `clock` | Источник времени. В работе `time.monotonic`, в тестах подменяется |

На одного клиента хранятся два изменяемых числа: `tokens` и `last_refill`. Ведро создаётся полным: `tokens = capacity`.

## Шаг 1. Пополнение (`_refill`)

Фоновый таймер не нужен. Токены пересчитываются в момент запроса, по прошедшему времени:

```python
def _refill(self) -> None:
    now = self.clock()
    elapsed = max(0.0, now - self.last_refill)
    self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
    self.last_refill = now
```

- `elapsed * refill_rate` это то, что накопилось за паузу.
- `min(self.capacity, ...)` не даёт ведру переполниться, сколько бы клиент ни молчал.
- `max(0.0, ...)` защита на случай, если часы вернули меньшее значение: время не может идти назад.

## Шаг 2. Решение (`consume`)

```python
def consume(self, n: float = 1) -> Decision:
    with self._lock:
        self._refill()
        if self.tokens >= n:
            self.tokens -= n
            return Decision(allowed=True, remaining=self.tokens, retry_after=0.0)

        retry_after = (
            math.inf if n > self.capacity else (n - self.tokens) / self.refill_rate
        )
        return Decision(allowed=False, remaining=self.tokens, retry_after=retry_after)
```

(Код сокращён: убраны проверка `n < 0` и комментарии.)

Порядок такой: досыпать, проверить, списать или отказать.

- **Отказ ничего не списывает.** Токены остаются как были.
- **`retry_after`** считается формулой: сколько секунд нужно, чтобы накопилось недостающее. Если `n` больше `capacity`, ведро столько не вместит никогда, и значение равно `inf`.
- **Замок** (`self._lock`) нужен потому, что три шага (досыпать, проверить, списать) должны выполняться как одна операция. Без него два потока прочитают одно и то же число токенов и спишут один токен дважды.

## Пример с цифрами

Ведро на 5 токенов, пополнение 1 токен в секунду. Результат получен запуском `TokenBucket` с фейковыми часами.

| Время, с | Запрос | Результат | Осталось | Повторить через, с |
|---|---|---|---|---|
| 0 | 1–5 | пропущены | 4, 3, 2, 1, 0 | 0 |
| 0 | 6 | отказ | 0 | 1.0 |
| 0.5 | 7 | отказ | 0.5 | 0.5 |
| 1 | 8 | пропущен | 0 | 0 |
| 1 | 9 | отказ | 0 | 1.0 |

Первые пять запросов проходят пачкой (это всплеск), потому что ведро было полным. После этого пропускается ровно один запрос в секунду.

## Что вокруг механизма

| Слой | Файл | Что делает |
|---|---|---|
| Ведро на клиента | `storage/memory.py` | Создаёт `TokenBucket` на каждый ключ и вызывает `bucket.consume(n)` |
| HTTP | `api/middleware.py` | Берёт ключ клиента, вызывает хранилище, превращает отказ в 429 и заголовки |
| Распределённый вариант | `storage/redis_store.py` | Тот же алгоритм внутри Redis |
| Нагрузка и картинка | `sim/`, `web/` | Только для демонстрации |

Зависимости идут в одну сторону: `api → storage → core`. `core` ничего не знает про остальные слои.

## Алгоритм записан в трёх местах

1. `core/bucket.py`: Python, для памяти процесса.
2. `_CONSUME_LUA` в `storage/redis_store.py`: тот же алгоритм на Lua. Это переписанная копия, а не вызов Python-кода: скрипт должен выполняться внутри Redis, чтобы шаги «прочитать, посчитать, записать» были атомарны.
3. `NaiveRedisStore` в том же файле: намеренно неправильная версия, которая читает, считает в Python и пишет обратно. Нужна только чтобы показать гонку.

При изменении алгоритма (формулы или правила отказа) править нужно и Python-версию, и Lua-скрипт. Тесты проверяют их по отдельности.

## Как проверить

```bash
.venv/bin/python -m pytest tests/unit/test_bucket.py -v
```

Тесты читаются как описание поведения, потому что время в них фейковое и без `sleep`:

- `test_starts_full`: ведро создаётся полным.
- `test_allows_burst_up_to_capacity`: всплеск ограничен размером ведра.
- `test_rejected_request_does_not_spend_tokens`: отказ ничего не списывает.
- `test_refills_over_time` и `test_refill_is_fractional`: токены возвращаются, в том числе дробными долями.
- `test_never_exceeds_capacity`: ведро не переполняется.
- `test_concurrent_consume_never_exceeds_capacity`: при 32 потоках проходит ровно `capacity` запросов.
