How to read the picture

The spike at the start. Buckets start full, so the first requests pass in a burst and the green area rises above the dashed line.

The flat shelf. Once a bucket is empty, exactly as many requests pass per second as tokens come back. Everything above that gets a 429.

The queue. A token bucket itself holds no queue: it lets a request through or answers 429. A queue appears on the client side, when a client waits for Retry-After and retries (“wait and retry”). If the client sends faster than the bucket refills, the queue grows and requests wait longer and longer. With “drop the request” there is no queue, and a 429 means a lost request.

A polite client is not affected. If a client sends less often than tokens return, its requests pass immediately. Every client has its own bucket.

Shared key and the race. Turn on “shared key” and pick “Redis (naive)”: parallel requests to one bucket read the same value, and more requests pass than should. With “Redis (Lua)” this does not happen.
